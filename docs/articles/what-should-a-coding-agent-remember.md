# What Should a Coding Agent Remember?

## Why write authority, scope, provenance, and staleness matter more than how much an agent stores

> **Disclosure:** I built [Second Brain for Pi](https://github.com/solodev1911/second-brain-pi). It appears near the end as one worked example, so this should not be read as an independent product comparison.

A coding agent helps diagnose an architectural problem. It traces a request across several modules, discovers a non-obvious dependency, and explains why an apparently redundant validation step must remain in place.

The next day, in a new session, the agent may not retain the conclusion.

The obvious response is: give the agent memory.

But that answer creates a harder set of questions. Should it save the whole conversation? Only the final answer? The files it inspected? Its failed attempts? Should the agent decide what matters, or should the user? What happens after the implementation changes? Is the remembered explanation still knowledge, or has it become misinformation?

For coding agents, forgetting is inconvenient. Remembering the wrong thing can be worse.

The useful question is not simply, “Does this agent have memory?” It is:

> What is being remembered, who authorizes it, how is it retrieved, and what happens when it conflicts with the current repository?

That question reveals a design space—not a single product category.

## “Memory” names several different problems

A transcript archive preserves what happened. A code index represents what exists now. A user profile stores preferences. An architecture decision record explains why a choice was made. They can all improve an agent’s future work, but they require different write and trust policies.

The broader research literature makes the same point. Surveys of LLM-agent memory treat it as a set of operations—such as consolidation, updating, indexing, forgetting, retrieval, and compression—rather than a synonym for storage ([Zhang et al., 2024](https://arxiv.org/abs/2404.13501); [Du et al., 2025](https://arxiv.org/abs/2505.00675)).

For coding work, I find it useful to distinguish six things an agent might remember.

### 1. Working context

This is the current request, recent messages, tool results, selected files, and active plan. Compaction can extend it, but working context is still temporary. It is short-term attention, not durable project knowledge.

### 2. Episodic history

This records what happened: which files were inspected, which test failed, what fix was attempted, and how the session ended. It is valuable for resuming interrupted work or auditing an agent.

The problem is that a session can contain several abandoned proposals and one final correction. Preserving the episode is not the same as identifying its approved conclusion.

### 3. Semantic knowledge

These are facts intended to remain useful beyond one interaction: “tax is applied after discounts,” “this customer is in the EU region,” or “the project uses a custom migration wrapper.”

This is the form most commonly associated with long-term agent memory. It also creates the clearest contradiction problem because facts change.

### 4. Procedural knowledge

This tells the agent how to work: run a particular test before merging, do not edit generated files, or ask for approval before deployment. `AGENTS.md`, contribution guides, editor rules, and skills belong here.

Procedural knowledge often should not depend on probabilistic retrieval. If a rule must always apply, a reviewed file loaded deterministically may be safer than a memory that might not be recalled.

### 5. Structural knowledge

This describes relationships in a repository: callers and callees, imports, ownership, paths, dependencies, and clusters. Repository maps and code graphs excel here because structure is relational.

Structural knowledge is usually derived from the current source rather than written by a person.

### 6. Experiential conclusions

This sits between history and documentation: why an intuitive fix failed, which module actually owns a behavior, which constraint was easy to miss, or what trade-off drove a local decision.

These conclusions can save hours in a later session. They are also risky because they may have been generated by a model, based on incomplete evidence, and made obsolete by later code.

That last category is where the write-policy problem becomes unavoidable.

## The hardest part is deciding what gets in

Most discussions of memory begin with retrieval: similarity ranking, graph traversal, and deciding which results enter the model’s context. Those choices matter. But before anything can be retrieved, something has to become durable.

There are four common write policies.

**Automatic capture** extracts memories from conversations in the background. It is low-friction and can build rich personalization. It can also store jokes, hypotheticals, abandoned plans, secrets, or model errors simply because they appeared in context.

**Agent-managed capture** lets the model decide what and when to store. This supports agents that learn continuously, but it gives a probabilistic system authority over its own durable state. Without safeguards, errors can reinforce themselves.

**Explicit user capture** requires a visible save action. It is predictable and makes consent legible. The cost is omission: users forget, and useful knowledge disappears.

**Repository-reviewed capture** promotes the knowledge through a normal file change, commit, or pull request. This provides a strong collaboration and audit model, but it is too heavy for every useful observation.

These policies can coexist. A coding environment might preserve session history automatically, let an agent retrieve code context, require explicit approval for experiential memory, and use Git review for team rules.

The important point is to choose deliberately. “The system remembered it” is not an adequate explanation of how a model-generated claim became durable.

## The alternatives solve different slices of the problem

Several distinct families emerge from current first-party documentation.

### Repository-native files: boring, portable, and often right

README files, architecture decision records, contribution guides, and agent instructions are still a strong baseline. They are human-readable, portable across tools, versioned with the code, and reviewable by a team.

Continue’s current [rules](https://docs.continue.dev/customize/rules) are a good example: Markdown files under `.continue/rules` can encode project-specific guidance. Its [codebase-awareness guide](https://docs.continue.dev/guides/codebase-documentation-awareness) emphasizes live exploration, search, Git, rules, and MCP; the earlier `@Codebase` provider is deprecated.

The weakness is retrieval and maintenance. Documentation becomes scattered, contradictory, or stale. Valuable investigation results often remain trapped in a chat because turning them into a polished ADR feels too expensive.

**Choose files when** the knowledge is stable, important to humans, and deserves normal review.

### Repository maps and indexes: current structure, not lived experience

Aider’s [repository map](https://aider.chat/docs/repomap.html) gives the model a compact view of important files, symbols, signatures, and dependency relationships. It uses graph ranking to select relevant portions that fit a token budget.

GitHub Copilot’s [repository indexing](https://docs.github.com/en/copilot/concepts/context/repository-indexing) uses semantic code search and refreshes the index as the repository changes. Continue and Cursor also provide live code exploration or indexing in their own environments.

These systems answer, “What code is relevant now?” They do not necessarily answer, “What did we learn about it last week?”

**Choose a repository map or semantic index when** the primary problem is navigation through current code.

### Structural code graphs: relationships first

Code graphs model symbols and their relationships directly.

[Graphify](https://github.com/Graphify-Labs/graphify/blob/v8/README.md) emphasizes code structure and graph traversal, and also includes work-memory features. [CodeGraph](https://github.com/codegraph-ai/CodeGraph) combines structural and semantic retrieval with explicit project-memory tools. [GitNexus](https://github.com/abhigyanpatwari/GitNexus) emphasizes architecture, execution flows, and change impact.

Their strength is relational navigation: “What depends on this?” and “How does this request reach that component?” A graph should still guide source inspection rather than replace it. Extraction can omit an edge, an index can lag, and a summary can lose detail.

**Choose a code graph when** cross-file relationships and change impact are central to the work.

### Hosted coding memories: integrated but platform-bound

[GitHub Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory) stores repository facts and user preferences. Repository facts include code citations and are checked against the current branch before use. As documented in September 2026, unused facts are deleted after 28 days, subject to successful validation and reuse resetting the timer.

[Cursor Memories](https://docs.cursor.com/en/context/memories) turns conversation-derived information into project-scoped rules. A background sidecar proposes memories for approval, while the agent can also create memories through tool calls. Users manage them in Cursor settings.

Both reduce manual maintenance, but use system-assisted memory selection rather than requiring every durable record to be written manually.

**Choose a hosted coding memory when** you already use that coding platform, value integrated memory, and are comfortable with provider-hosted, platform-specific records.

### Semantic memory frameworks: flexible recall across interactions

[Mem0](https://github.com/mem0ai/mem0) provides APIs for adding, searching, updating, deleting, and tracking memory. Its optional [Graph Memory](https://docs.mem0.ai/open-source/features/graph-memory) extracts entities and relationships alongside embeddings.

[LangMem](https://github.com/langchain-ai/langmem) provides primitives for semantic, episodic, and procedural memory. It supports both writes made during the active agent turn and background extraction from conversations, while leaving storage and policy customizable.

These frameworks are attractive when users will not remember exact wording. For example, they are designed to retrieve a note written as “billing calculation” from a query about “invoice totals.” Their flexibility also means the application must define identity, scope, contradiction, provenance, and deletion correctly.

**Choose semantic memory when** fuzzy recall and personalization matter more than exact code relationships.

### Stateful agents: memory as persistent identity

[Letta](https://docs.letta.com/v1-sdk/concepts/stateful-agents) treats the agent itself as persistent. Memory blocks can remain in context, be shared across agents, and be attached or detached as needs change. This continues the virtual-memory direction introduced by [MemGPT](https://arxiv.org/abs/2310.08560), which moved information across memory tiers to extend effective context.

This is a natural fit for an agent expected to maintain a personality, user relationship, or long-running state. It is not identical to repository truth. What one agent has learned across projects may be inappropriate in the next repository it opens.

**Choose stateful agents when** persistent identity and continuously available state are core requirements.

### Temporal and corpus graphs: richer models for different jobs

[Graphiti](https://github.com/getzep/graphiti) builds temporal knowledge graphs from episodes. Facts have validity windows; superseded history is preserved; retrieval can combine semantic, keyword, and graph methods. This is powerful for changing entities such as customers, policies, roles, or inventory.

[Microsoft GraphRAG](https://microsoft.github.io/graphrag/) extracts a graph and hierarchical community reports from a document corpus. It supports local, global, DRIFT, and basic vector search. It is designed for corpus-level synthesis rather than session memory for a coding agent.

[Cognee](https://github.com/topoteretes/cognee) spans several categories, combining documents, code, conversations, graph structure, vectors, session memory, and explicit `remember`/`recall`/`forget` operations.

**Choose a temporal graph when** changing relationships and historical validity matter. **Choose a corpus graph when** the task requires synthesis across many documents. **Choose a hybrid memory platform when** one application needs several retrieval modes behind a common interface.

## When memory disagrees with code

Imagine an agent remembers:

> `calculate_total` adds tax directly to the subtotal.

Later, the function keeps the same name but applies a service fee and discount first. A semantic search can still retrieve the old explanation. A graph link can still point to the existing symbol. Neither proves that the conclusion remains true.

A robust record should ideally include its time, scope, claim type, and supporting sources. Retrieval should distinguish “this was previously concluded” from “this is currently true.”

For implementation questions, current source is usually the strongest evidence of what the software does now. Even that needs nuance: code may be authoritative about behavior while an architecture decision record is authoritative about intent. A regression can put the two in conflict.

The safest pattern is not to make memory silently outrank everything else. Retrieve it with provenance, inspect the current authority, and explain the disagreement.

This also changes how memory should be evaluated. Successful fresh-session recall is not enough. A serious test should alter behavior while preserving symbol names, rename symbols without changing behavior, correct a prior conclusion, ask unrelated questions, switch repositories, and delete the record.

Useful metrics include stale-memory obedience, irrelevant retrieval, unexpected writes, correction behavior, cross-project leakage, and ease of inspection and deletion.

## One narrow design point: Second Brain for Pi

Second Brain is an opinionated Pi integration built on Graphify. It is not an original graph engine, and Graphify already supports work memory and reflection.

This integration’s design emphasis is the write boundary.

Each repository has its own graph and memory directory. Pi can use Graphify to explore architecture and saved conclusions. After Pi produces a completed answer, the user may invoke `/remember`. The extension captures that answer, stores it as readable Markdown, and links it to repository graph nodes when the same turn produced suitable evidence. Later sessions can retrieve the record through graph queries.

The package enforces that explicit write path for its own memory writer, captures from the current conversation branch, reuses exact duplicates, scopes output per repository, and confines resolved roots to the project. It instructs Pi to query the graph first for repository-structure questions and to verify remembered conclusions against current source. Those last two are workflow instructions, not formal guarantees of tool order or correctness. A source link establishes traceability, not truth.

The trade-offs are explicit-capture friction, Graphify’s indexing complexity, uneven platform maturity, and the absence of hosted team sync or cross-project memory.

Storage is local to the repository, but that does not make the whole workflow offline: Pi may send prompts, selected source, graph results, and distillation material to the model provider configured by the user.

The most defensible description is therefore modest: Second Brain is one option for Pi users who want to deliberately promote a small number of completed, project-specific conclusions into inspectable memory that can be source-linked when same-turn graph evidence supports it.

### Graphify is not Graphiti

The names are easy to confuse. **Graphify** is the repository/corpus graph engine used by Second Brain. **Graphiti** is Zep’s temporal knowledge-graph framework. They are different projects with different maintainers and goals.

## Start with the smallest memory that matches the problem

Use reviewed files for stable team instructions, session history for resuming work, a map or index for repository orientation, a code graph for relationships and impact, semantic memory for fuzzy personalization, stateful blocks for persistent identity, and temporal graphs when historical validity matters. If the goal is to preserve a few user-initiated repository conclusions, consider explicit project-scoped experiential memory.

The goal should not be maximal recall. It should be useful continuity with clear authority, scope, provenance, and correction.

A coding agent’s memory is better governed when users can see why something was saved, trace its evidence, revalidate it against current authorities, and remove it when it is no longer useful.
